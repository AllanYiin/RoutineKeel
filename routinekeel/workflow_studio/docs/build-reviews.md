# 建置、驗收與審核

「建置歷史／審核／報告」列出候選包、技術結果及目前審核狀態，並提供歷次報告、
受控文字檔預覽、審核理由與保存事件分頁。程式預覽不執行內容，最多顯示 128 KB；
事件每頁 50 筆、長文字節錄，原始紀錄仍保留在資料庫。

技術試做與人工判斷分開：

- 送審需有通過報告、完整有效案例清單及未過期的來源版本。
- 退回保存理由，撤回同一流程 Revision 的有效核准，不改寫舊報告。
  重新編譯相同 Revision 不能繞過退回；必須重新試做、再次送審，或建立新的修訂。
- 新報告記錄開始試做時的 review_sequence，不能以退回前已存在或已開始的報告重新送審。
- 撤回核准只影響後續發布資格，不自動停止已安裝工作流。
- 未發布且沒有有效核准的建置可封存／恢復，檔案與報告不刪除。
  已有發布或準備紀錄者受到保護，目前必須先核對發布狀態，不能直接封存；
  未完成發布準備的清理／核對 UI 仍須補齊。

封存不是取消正在進行的工作；已開始的試做可能完成並留下歷史報告，但封存狀態仍阻擋核准與新操作。
已封存的專案不能新建候選、開始試做或核准／發布新版本，先恢復專案後才能繼續設計。
歷史回復僅適用於原先成功發布的核准版本，不能用 historical 參數繞過一般發布 Gate。

核准及發布前會重新核對目前所有有效案例，不允許新增案例後沿用較小的舊驗收集合。
案例指定的交付物不能被重新綁到另一個成果。來源版本更新後，案例不會自動改寫；
可在案例編輯器明確選擇「改用來源目前版本」，先看預覽，再另存案例新版並重測。

相同套件、報告、操作者及理由的重複核准會回傳原紀錄；新的報告會形成新的核准。
相同核准的重複發布不建立重複版本；新的核准即使 manifest bytes 相同，仍保留新的決策關聯。
相同 manifest 的準備 journal 不足以證明新核准已生效，正常發布須明確提交 current 指標；
因此被退回的準備不會只因 hash 相同就誤判已發布。封裝 ZIP 的時間與模式欄位採固定值，避免檔案 mtime 改變內容指紋。

發布歷史也提供「停用選取的目前發布版本」，記錄操作者與理由，保留既有成果。
若選取的已不是目前版本，操作會拒絕；停用不會取消已開始的 Run。
新視窗與操作入口尚未實機走查，程式測試不能代替視覺／互動驗收。
