# 發布中斷後核對

在「發布歷史與版本回復」選擇「核對未完成發布準備」，選取準備紀錄，
核對結果會顯示原工作區、工作流與判定理由。填入操作者及理由後才套用。

| 實際狀態 | 可執行操作 |
|---|---|
| 正式套件及指標已生效，或 journal 與完整的新套件證明切換已發生 | 補齊指標及發布／停用紀錄 |
| 原版本仍完整、首次發布尚無正式 manifest，或已被另一個完整版本取代 | 結束未生效準備，記為 abandoned |
| 檔案損毀、內容不符、工作區位置缺失或歸屬不符 | 拒絕套用，保留原狀供核對 |

核對、套用及讀取目前版本時的自動補齊均先取得發布鎖，工作區正在發布時不進行判定。套用會重新核對
觀察內容的 hash；指標、套件完整性或核准／審核狀態變更後須重新檢查。
相同 manifest 不能證明新的核准已提交：尚未切換指標時保留原版本。
若已知前一版本完整但 current 指標遺失，結束準備可以補回該指標。

此操作不安裝新的程式、不執行流程、不刪除套件、暫存檔或成果。
已生效版本的事實紀錄不代表重新核准；核准撤回或審核失效會顯示提醒，
必要時另外停用已安裝版本。停用途中中斷也依實際 manifest 狀態核對，
不會把已停用的版本偷偷恢復成可執行。

結束準備後，沒有有效核准及其他發布參照的建置可再封存。
後續首次發布僅允許旁邊存在已核實的 abandoned 殘留：完整 wheel 必須符合保存快照，
原子寫入暫存檔須符合已知檔名及快照內容前綴。所有殘留仍保留；
使用者檔案、未知檔案、子目錄或被修改的內容仍會阻擋覆寫。

每次人工套用會保存不可變的觀察快照、指紋、操作者、理由與結果。
資料庫決策及稽核紀錄同交易；若稽核寫入失敗，資料庫回復原狀。
補齊檔案指標與資料庫不能形成跨媒介交易：若中間失敗，指標可能已補回，
重新核對可繼續完成；不因此重裝套件或重跑工作流。

核對單檔最多 128 MiB，狀態 JSON 最多 1 MB；超過限制拒絕處理。
新版資料庫與備份／回退方式見 [遷移策略](migration-strategy.md)。
服務與 UI model 已有故障測試，新視窗仍待原生桌面互動與視覺驗收。
