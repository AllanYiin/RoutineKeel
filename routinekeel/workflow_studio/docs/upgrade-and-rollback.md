# 備份、升級與回滾

## 摘要與適用範圍

適用 Studio 0.1.0、schema v014。這是維護者的資料保護操作指南，
不是「已有正式新版本可升級」的通知。首次正式發行包與乾淨安裝仍待完成。

## 相容性（Compatibility）與不相容變更

開啟工作區會檢查並可能遷移資料庫；未知較新 schema 會拒絕，不可手動降低 user_version。
程式升級、Studio 資料還原、已發布流程版本回復是三件不同的事。
只換回舊 wheel 不會把資料庫降版；回復 Studio 資料也不會自動切換另一位置的正式流程。
各次 schema 的備份與新增內容見[遷移紀錄](migration-strategy.md)。

## 升級步驟

1. 記錄目前 Studio 版本、底座版本、專案工作區及每個發布工作區的位置，保留原安裝包與校驗資料。
2. 等待進行中的分析、試做及發布結束，關閉所有會寫入此 Studio 工作區的介面／程序。
   若要備份 Runtime 成果，也要讓對應工作區停止寫入。不要強制結束正在提交的工作。
3. 將整個專案工作區複製到新的日期備份資料夾；發布在其他位置時，分別複製那些工作區。
   完整備份不能只複製 studio.sqlite3。至少保留以下資料：

   ```text
   專案工作區/share_states/workflow_studio/  # DB、備份與 projects 建置/報告
   發布工作區/.studio_releases/            # journal、快照、版本指標
   發布工作區/<workflow_id>/              # manifest、wheel、既有成果
   ```

4. 在新的練習目錄建立備份副本，先用預計升級版本開啟這份副本。正式目錄保持關閉且不覆寫。
5. 讀取專案、來源歷史、案例及發布紀錄；用非敏感案例在新的測試位置試做。
6. 確認資料及功能正常後，才安排正式工作區升級。首次開啟前仍保留剛才的完整備份。

SQLite 遷移會先建立一致性的 before-vNNN 資料庫備份及 checksum，再於交易內更新 schema。
自動資料庫備份不包含所有建置／測試產物，也不取代上述完整工作區備份。
可重跑的備份還原檢查由 `SQLiteRepository.backup`／`restore` 提供，restore 只能寫入新目的地。

## 驗證（Verify）

至少核對專案數、目前 Revision、來源與案例版本、已核准／已發布指紋，以及一個實際 Runtime 試做。
比對原先的 manifest 與成果，確認 Studio 升級沒有改動正式發布內容。
`status` 命令可以回報版本與 schema，但開啟動作可能觸發遷移，不能拿它當成備份前的唯讀探測。
完整 schema 備份測試已存在；真人依本頁執行整包升級／回退與最終發行包演練仍待驗收。

## 回滾（Rollback）

升級失敗時停止對該工作區繼續寫入，先把升級後的整組資料另存，保留新產生的證據。
把升級前完整備份複製到另一個新的目錄，使用相容舊版程式開啟；不要以舊 DB 覆蓋現有新資料，
也不要讓舊程式強行寫入新版 schema。重新做上節驗證後，再決定哪個目錄成為後續使用位置。
備份時間之後新增的資料不會存在於舊備份，必須保留升級後副本以便核對，不能宣稱自動合併。

若只要回復某個已發布流程，使用工作台「發布歷史／回復舊版」。核准已撤回、工具政策改變，
或快照不完整時可能拒絕回復；先查原因，不要手動改 current.json 或重新拼湊套件 hash。
遇到 prepared／結果不明的發布，依[發布恢復](release-recovery.md)核對實際檔案狀態。

## 已知問題（Known issues）

本版沒有一鍵匯出完整備份或任意 schema 降版工具。備份以確定停止寫入後的完整副本為準。
備份可能含私人來源、生成程式、模型文字及成果，保存與分享方式見[隱私指南](privacy-and-model-usage.md)。
