## 參與者與觀察者分工

1. 觀察者建立新的 Studio 工作區，先完成模型設定、核對費率與預算。不得預載本資料集的參考程式或直接灌入 IR。
2. 每件建立獨立專案，名稱與目標參考該件 `authoring/brief.txt`；成功條件與比較規則在 catalog 中固定。
3. 參與者只取得該件的 `authoring/` 與 `training/`。匯入後可 Ctrl／Command 多選來源一起分析，範圍預覽須列出全部選取來源。
   成功資料夾案例可選 `training/` 使用本機「從成功案例找流程」；C15 含中間成果。
4. 用 training 的 input／output 建立固定案例，依原規則選 exact_bytes 或 json_equal，完成分析、修改規則、試做與必要的產品內修復。
   不可為了通過而放寬比較方式、改預期結果、寫 Python 或修改設定檔。一般產品操作及業務釐清不算手動寫程式。
5. 訓練試做通過並固定候選後，觀察者才加入 `held_out/` 的兩組案例，重新試做。**不要把 held_out 選為分析來源，也不要在這輪失敗後啟動會傳送差異／預期結果的模型修復。**
   若未見資料已被模型看到，本次不得計為獨立未見驗收；須記錄 exposed，另設新的獨立樣本。
6. 全部案例通過後，使用正常審核／發布操作至隔離測試工作區，保存套件指紋、報告與 release ID。
   發布與模型呼叫仍遵守原授權，不能因這份指南自動使用付費服務或外傳私人資料。

觀察者從 `results-template.json` 複製一份到 `dist/acceptance-campaigns/<新批次>/results.json` 記錄結果，
參與者不必編輯這份檔案。每件須記錄參與者非技術身份、是否手改程式／設定、來源暴露、模型、
訓練與未見報告 ID、package hash、release ID、耗時及所需協助。
未執行／預算受阻／缺少資料不能填 passed。至少 16 件由非技術參與者獨立完成，且有對應實際報告，才可滿足原真人 Gate。
正常的產品內修正可以記入完成過程；若修正使用了未見資料，須分開記錄，不能冒充第一次未見驗收通過。
「非技術使用者完成轉換」與「固定候選的未見資料品質」是兩項紀錄，不另增原規格沒有要求的首輪全過門檻。
若真人或模型尚未執行，即使參考算法和所有 fixture 測試通過，該 Gate 仍未達成。

## 資料版本與驗證

`catalog.json` 固定每個檔案的 SHA-256、來源角色、比較規則及訓練／未見分離。
`acceptance_oracle.py` 是只供測試資料審查的獨立參考實作，沒有呼叫 Studio 的轉換工具，
也不會被放入 Discovery 來源。輸出資料以固定檔案保存；checksum 類案例依明確的標準 SHA-256 計算。
測試逐一核對 61 組固定預期成果、所有來源可預覽，以及實際 PreparedDiscovery 不包含 held_out 的檔案參照。
準備資料不呼叫模型。

五個成功資料夾另有工程端到端測試：從 training 推導候選、編譯、重播訓練及兩組未見資料，
再經 fixture 核准發布至隔離工作區；C15 真正使用中間產物形成兩步流程。
這項測試不會更新 results-template 的真人結果。C10 的無匹配情境保留零位元組預期檔，
匯入檔案路徑支援空檔；空白貼上說明、NUL 二進位、空白 JSON／Mermaid 仍拒絕。

```powershell

```

`build_acceptance_corpus.py` 是維護者的建置來源，不是參與者的操作步驟。v1 一旦投入正式測試就保持不變；
修正資料或規則須另建資料集版本並重新記錄指紋，不得為配合模型輸出覆寫既有答案。
不要匯入整個 acceptance_v1 根目錄，因為它含觀察者專用的 held_out 與結果模板。
