# Studio 重新設計：宿主推理互動規格（草案，待確認）

狀態：草案，未取代 `requirements.txt`。第 1 到 12 節是第一版互動模型，已實作於 `src/workflow_studio/guided/`（進度見第 12 節）。2026-11-19 由流程作者本人試用後，互動模型改為第 13 節的做法；第 13 節尚未實作，與前文衝突時以第 13 節為準。
這份文件要回答的問題：**作者不填表單、只做確認與選擇時，人、宿主 Agent、Studio 各自負責什麼，資料怎麼流動。**

已定案的前提（使用者 2026-11-19 決定）：採方案 A，設計期推理只靠宿主模型，Studio 自己不呼叫模型、不需要 API 金鑰。

## 1. 範圍

納入：

- 以對話加卡片取代表單的設計期互動。
- Studio 的 MCP server、一份 MCP App HTML、本機頁面轉接。
- 反思分流規則、技術選擇卡、人工核准的強制方式。

不納入：

- flow_base、既有流程包、Workflow IR v1 schema、Compiler、Verifier、發布與回滾機制。這些沿用。
- 執行期 LLM 節點（FR-15）。流程執行時沒有宿主，`llm` 節點仍需自己的端點與預算，規則不變。
- 影片分析（P2，維持停用）。

## 2. 四個角色

| 角色 | 負責 | 不可以做 |
| --- | --- | --- |
| 作者（人） | 提供材料、確認、選擇、核准、發布 | 無 |
| 宿主 Agent | 讀材料、草擬流程、回應反思清單、撰寫卡片文字 | 自行標記 `verified` 或 `human_confirmed`、核准、發布 |
| Studio server | 保存狀態、驗證契約、產生反思清單、分流成卡片、試做、強制核准規則 | 呼叫模型、執行來源或模型輸出中的指令 |
| UI（MCP App 或本機頁面） | 顯示卡片、收集人的動作 | 推理、直接寫檔 |

宿主推理不使用 MCP sampling（2026-07-28 核心規格已標為 deprecated，MCP Apps 的 iframe 也沒有 sampling 方法）。推理一律發生在宿主對話內：Agent 讀工具回傳，再用工具把結果寫回。

## 3. 互動流程

1. **開始**：作者在宿主對話說出想做的事，或直接開啟 Studio。不需要先建立專案或填目標；專案在第一份材料進來時自動建立，名稱由 Agent 提議。
2. **給材料**：作者提供成功案例資料夾路徑、貼上文字或流程圖。UI 顯示實際預覽與「這些內容會交給宿主模型閱讀」的範圍確認。
3. **回述**：Agent 用白話回述「我理解你的工作是…」，內容串流顯示在對話中。
4. **草擬與反思**（第 4 節）：作者不參與，UI 只顯示進度。
5. **確認卡與選擇卡**（第 5 節）：作者逐張處理。UI 一開始就顯示總數與其中需要回答的題數。
6. **試做**：Studio 用固定案例在隔離工作區試做並比對。失敗時 Agent 依差異修正，最多兩輪，之後呈現失敗證據。
7. **核准與發布**：作者在 UI 核對成果後核准並發布。這一步只接受人的動作（第 7 節）。

任何時候關閉再開啟，都從已保存的狀態繼續。

## 4. 草擬、反思、分流

**草擬**：Agent 提交完整 IR 候選與每項主張的證據位置。Studio 驗證 schema、證據位置確實存在於來源中、工具在允許清單內。Agent 送出的標記只接受 `observed`、`inferred`、`conflicted`。

**反思**：草稿在通過反思前狀態為 `needs_reflection`，不會產生卡片。反思清單由 Studio 以確定性檢查產生，不是由模型自評：

- 沒有證據位置的主張。
- 不同案例之間互相矛盾的觀察。
- 候選流程在訓練案例上重播後與正確成果的差異。
- IR 驗證通過但 Compiler 不支援的功能。
- 有外部副作用、或會把資料送出本機的步驟。

Agent 必須逐項回應，回應只有三種：已修正（附新草稿）、降級為問題（交給人）、保留並說明理由。未回應完不得進入下一步。反思最多兩輪。

**分流**：由 Studio 依規則決定，Agent 不能改變分流結果。

| 條件 | 呈現方式 | 人的動作 |
| --- | --- | --- |
| `observed`，證據位置有效，且重播一致 | 自動填入，收合顯示 | 無，可展開查看 |
| `inferred` | 確認卡 | 正確／修改 |
| `conflicted`，或缺少資訊且會改變成果 | 問題卡（選項優先） | 選一個 |
| 允許清單中有兩個以上可行做法，且在費用、可重現性或人工負擔上有差異 | 技術選擇卡 | 選一個 |
| 缺少資訊但不影響成果 | 採預設值，列在摘要 | 無 |

**不問人的技術欄位**：下列欄位由 Studio 推導，不出現在任何卡片上，只在進階檢視中唯讀顯示。

| 欄位 | 推導來源 |
| --- | --- |
| `cache_policy`、`retry_policy` | `side_effects`：`external` 一律不快取、不自動重試 |
| `platform_requirements` | 工具簽章的平台交集 |
| `timeout_seconds`、`resources` | 工具簽章預設值，試做實測後調整 |
| `preconditions`、`postconditions` | 輸入存在與輸出非空為基本條件，其餘由已確認的業務規則轉成 |
| `tool_version`、`evidence_refs` | Registry 與草稿 |

## 5. 卡片契約

所有卡片共同欄位：穩定 ID、對應的 IR 位置、證據位置清單、狀態（待處理／已確認／已修改／已選擇）。狀態同時用文字與圖示表示，不只靠顏色。

**確認卡**：一句業務語言的敘述，加上「依據」連結可開啟原始來源位置。按「修改」時先給 Agent 提出的替代選項，最後才是自由輸入。

**問題卡**：一個問題、二到四個選項，並說明為什麼 AI 無法判斷（例如哪兩個案例互相矛盾）。

**技術選擇卡**：

- 選項是封閉集合，只能來自 Registry 允許清單與節點種類（確定性、執行期 LLM、人工確認）。Agent 不能新增清單外的選項。
- 每個選項固定用五個面向描述優缺點：費用、每次結果是否相同、需要多少人工、支援平台、資料是否離開本機。
- 五個面向的事實由 Studio 從工具簽章填入；Agent 只負責把事實寫成白話，以及寫建議理由。
- 建議理由必須引用證據位置。沒有證據支持時不標示建議。

## 6. MCP 介面與宿主轉接

Studio 新增一個 stdio MCP server，與 flow_base 既有的 `mcp_stdio` 分開，沿用 `mcp==2.3.0`。所有工具都回傳有意義的文字內容，宿主不顯示 UI 時流程仍可完成。

Agent 可呼叫的工具（名稱暫定）：

| 工具 | 用途 |
| --- | --- |
| `studio_open` | 開啟或接續專案；回傳 UI 資源或本機頁面網址 |
| `studio_state` | 目前階段、待處理事項、下一步該做什麼 |
| `studio_source_read` | 分段讀取已獲作者同意的來源 |
| `studio_submit_draft` | 提交 IR 候選與證據 |
| `studio_reflection_items` / `studio_submit_reflection` | 取得與回應反思清單 |
| `studio_submit_card_text` | 提交卡片白話文字與建議理由 |
| `studio_trial` / `studio_trial_report` | 啟動試做（回傳 ID）與查詢結果 |
| `studio_submit_repair` | 依試做差異提交修正 |

只接受 UI 動作的操作：匯入來源、同意來源交給模型閱讀、回答卡片、核准、發布、回滾。

宿主轉接：

- 支援 MCP Apps 的宿主：工具以 `_meta.ui.resourceUri` 指向 `ui://` 資源，內嵌顯示。
- 不顯示 MCP Apps 的宿主（查證時 Claude Code CLI 屬此類，Codex 依版本而定）：`studio_open` 回傳 `http://127.0.0.1:<隨機埠>/` 的一次性票證網址，同一份 HTML 在瀏覽器開啟。做法比照 SkillNow。
- 兩者都不可用：文字模式。卡片以編號清單呈現，核准與發布不開放（見第 7 節）。

大型內容一律分段回傳。Claude 的工具結果超過約 15 萬字元會影響 App 顯示，Claude Code 預設上限為 25,000 tokens。

## 7. 核准與發布必須是人

MCP Apps 的工具可見性不是安全邊界，不能只靠把工具設成 app-only。採用以下做法（第 10 節決定 1）：

- 核准、發布、回滾只由本機頁面的工作階段接受，該工作階段以一次性票證建立，並檢查 Origin 與 CSRF。MCP 工具面沒有對應工具。
- 內嵌的 MCP App 在核准步驟顯示「在本機頁面完成核准」的入口。
- 經對話轉述的卡片回答標記為「轉述」，在核准畫面重新列出，由作者一次確認。
- 核准仍綁定套件指紋與驗收版本，內容一變就失效。這條沿用現有規則。

## 8. 隱私與用量

- 來源內容會進入宿主模型的對話。作者同意範圍之前，`studio_source_read` 不回傳內容，只回傳檔名與大小。
- 設計期 token 用量落在宿主對話，Studio 無法計量，介面明確標示「無法取得」，不估算。
- 設計期與執行期用量分開的原則不變。

## 10. 已決定事項

使用者於 2026-11-19 確認三項都採選項 A：只在本機頁面核准（接受僅綁 127.0.0.1、隨 MCP server 行程存活的短暫監聽作為「本機無常駐服務」的例外）、在本機頁面選檔、Tk 工作台凍結並於新介面驗收後移除。下表保留當時比較過的選項。

**決定 1：核准的強制方式**

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| A. 只在本機頁面核准（建議） | 是真正的邊界，Agent 碰不到；SkillNow 已驗證 | 內嵌顯示時要多開一次瀏覽器；需要短暫的本機 HTTP 監聽 |
| B. UI 顯示一次性確認碼，由人輸入 | 不需要本機 HTTP | 確認碼可能經工具結果被模型看到，邊界較弱；多一個輸入動作 |
| C. 只靠工具 app-only 可見性 | 最簡單 | 規格明說不是安全邊界 |

選 A 與「本機無常駐服務」的既有原則有出入：監聽只在 MCP server 行程存活期間存在、只綁 127.0.0.1、隨機埠。此例外已獲確認。

**決定 2：作者怎麼選本機資料夾**

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| A. 在本機頁面用拖放或檔案選擇（建議） | 最接近一般人的習慣 | 內嵌 MCP App 中是否可用未查證，可能要跳到本機頁面 |
| B. 在對話貼上路徑 | 所有宿主都可用 | 一般人不熟悉路徑 |
| C. server 彈出系統檔案對話框 | 操作直覺 | 由背景行程彈出視窗，各平台行為未驗證 |

**決定 3：既有 Tk 工作台與設計期 Provider**

| 選項 | 優點 | 缺點 |
| --- | --- | --- |
| A. 凍結不再新增功能，新介面驗收後移除（建議） | 過渡期有退路；不提前刪除已驗證的程式 | 過渡期兩套介面並存，文件要標清楚 |
| B. 立即移除 | 維護面最小 | 新介面未驗證前沒有可用入口；Stage 11 到 13 的既有證據作廢 |
| C. 長期保留為進階入口 | 進階使用者可直接編輯 | 每次改服務層都要顧兩套 |

## 11. 第一個垂直切片與驗收

範圍：文字加成功案例資料夾，走完「給材料、草擬、反思、卡片、試做、核准、發布」，只做確定性節點。

驗收方式：

- 用 acceptance-v1 既有案例，新舊介面用同一案例、同一計數方法量測「作者必須輸入文字的次數」與「必須做出的決定數」。目標值待舊介面實測後訂定，不先寫數字。
- 沒有 `llm` 節點的流程，發布後執行期模型呼叫數為 0（沿用 AC-05）。
- Agent 嘗試自行核准或標記 `human_confirmed` 的負向測試全部被拒。
- 原規格「20 件中至少 16 件由非技術使用者自行完成」的 Gate 不變，改在新介面上執行。
- 至少在 Claude Desktop（內嵌）與 Claude Code（本機頁面）各走一次真人操作；Codex 視當時版本實測後記錄結果。

## 13. 試用後修訂的互動模型（2026-11-19 至 11-20，尚未實作）

第 3 到 12 節的做法於 2026-11-19 由流程作者本人在 Claude Code 桌面版試用，停在第一步「給材料」，沒有走到草擬與發布。作者改以「為 AI 虛擬 IP 製作 Reel 並發布至粉絲團」示範他要的互動，並在對話內做完一次紙上演練。本節記錄因此確認的做法。引用作者原話時逐字照錄；標示為 Agent 推測、Agent 整理或 Agent 判斷者，尚未經作者確認。

### 13.1 試用卡住的地方

1. 起點要求先給材料。`studio_open` 在沒有任何材料時卻回覆下一步是 Agent 提交草稿，與 server 指示「作者先給材料」不一致。
2. 可用步驟只有 8 個檔案進、檔案出的確定性工具。作者要做的生成、人類審核、對外發布都沒有對應步驟，而且要等宿主查了清單才知道。
3. 選資料夾上傳失敗，頁面顯示「Invalid string length」。原因是整包讀進記憶體轉成單一 JSON，超過瀏覽器字串長度上限。沒有選個別檔案的入口，也不篩選。
4. 文字框打了字但沒按加入時沒有任何提示。宿主看不到頁面上的錯誤，只能請作者截圖轉述。
5. 對話與另開的網頁來回切換。頁面無法通知對話，每次換手都要作者回對話打字。
6. 驗收以逐字重現期望輸出為準，生成類的產出無法這樣驗。

### 13.4 逐層確認

起點是作者的一句任務。之後每一層都由 Agent 先猜、人修正，一層確認完才進下一層。

| 層 | 內容 | 人做什麼 |
| --- | --- | --- |
| 0 一句任務 | 作者用一句話說出要做的事 | 輸入一句話 |
| 1 釐清 | Agent 在背景以第一性原理拆解，只用是非題與選擇題反問 | 點選 |
| 2 步驟骨架 | Agent 推測步驟並畫成流程圖，標出每項材料是設定一次還是每次變動 | 修正步驟 |
| 3 輸入輸出 | 整條流程每次要給什麼、最後產出什麼，以及每一步的輸入與輸出 | 修正 |
| 4 工具清冊 | Agent 掃過流程圖彙整成一份清冊，標出每個工具用在哪些步驟 | 在清冊上填入或修正 |
| 5 檢核清冊 | 每項產出是機器檢核、人類審核，或不檢查 | 修正 |
| 6 審核方式 | 對人最省力的審核方式與審核地點 | 選擇 |
| 7 任務設定檔 | 把變數分成三類，抽出設定檔 | 修正 |
| 8 產生藍圖包 | 彙整成 13.7 的藍圖包 | 無 |

層的順序依作者示範的八步。作者原本把每步的輸入、輸出、工具與技能放在同一步，本表拆成第 3、4 層是 Agent 整理。

各層的規則：

- **第 1 層**：背景推理不顯示給人看（Agent 推測，作者未修正）。能合理推測的先猜，不先問。
- **第 2 層**：預設一條線依序執行。步驟之間誰需要誰的產出，記在各步驟的輸入裡，不因此改成平行。
- **第 3 層**：不可省略。「你少了輸入輸出設定   輸入不應該只有腳本，應該還要加入人類輸入的這個腳本的製作重點以及方向提醒」。每次輸入除了主要材料，還要有人對這一次的製作重點與方向提醒。
- **第 4 層**：不逐步驟讓人填。以工具為主、步驟為輔，讓人對清冊修正。
- **第 5 層**：人類審核是流程裡的正式步驟，不是事後補上的確認。
- **第 7 層**：變數至少三類：每次輸入、設定一次、Agent 當下判定。「非主角音色…背景音樂風格與使用時機…都應該是由Agent當下判定」。Agent 當下判定的項目要留下判定理由。

### 13.5 互動原則

| 原則 | 作者原話 |
| --- | --- |
| 起點是一句任務，不是材料 | 示範的第一步是「[列出任務]」；「我們先不處理提供歷史作業資夾」 |
| 反問用封閉題 | 「反問的題目盡量以是否題選擇題的方式來呈現」 |
| 漸進式揭露 | 「不需要合成一張，你忘了給很多題目只會讓使用者困擾，基於漸進式揭露， 讓使用者一次專注在有限的問題中」 |
| 預設線性執行 | 「建議不要主動把流程執行壓成高度平行，除非有時限限制，若無特殊要求維持線性最保險」 |
| 標出材料的收集頻率 | 「需要在流程圖上協助判斷哪些材料是收集一次就好有些是每次都變動的」 |
| 用清冊確認工具 | 「你掃過一遍流程圖，然後整理出一個工具清冊，然後可以現是哪些步驟需要此工具」 |
| 沿用作者的用詞 | 「我都講封面禎以及首禎」 |
| 給材料時不能只有整包上傳 | 「你的介面是要我傳整個資料夾，又沒法傳送個別檔案，所以應該是上傳後你自己要做篩選才對」 |

Agent 的落實方式（未經逐項確認）：一次一題，下一題依前一題的答案決定；只問會改變當前這一層結果的題目；凡是要人提供資訊的畫面，輸入處必須在同一張畫面上。

### 13.6 對話內呈現

- 是非題、選擇題、文字輸入由宿主直接在對話內顯示。「那些顯示不出來?是非題/選擇題／文字輸入  明明你都可以做到」。顯示不出來的只有 Studio 自己提供的 `ui://` 畫面。
- Agent 判斷（未定案）：Studio 不自帶畫面，改回傳結構化的題目資料與樣式規格，由各宿主用自己的方式畫。
- **視覺識別**（已定案）：題目區塊用亮橙配灰，要明顯有別於一般對話。「目的是要拉出這段與一般對話的差異感，讓使用者知道這是一個收集工作經驗轉工作流的應用」。示範配色為 `#FF6B00` 識別列加純黑字、灰底外框、選取後整塊亮橙。橙底上的文字只能純白或純黑，不可用灰。灰色部分使用宿主的顏色變數，才會跟著深淺色模式切換。

在 Claude Code 桌面版實測到的行為：

- 宿主內建的提問對話框點一下就直接回到 Agent，不能自訂外觀。一次出多題時，作者不作答而直接送出別的訊息，那幾題等於被略過。
- 對話內的 HTML 互動卡片外觀可完全控制，但點選只會把答案帶進輸入框，作者還要再按一次送出。
- 回合結尾的下一步按鈕是一鍵完成。

宿主是否內嵌顯示 MCP App（2026-11-19 查證）：Claude Code 的官方文件與 changelog 找不到支援的記載；Codex 桌面版依其 issue 與 changelog 有內嵌顯示，在 Windows 是否顯示未證實。

### 13.7 產出物是藍圖包

Studio 與對話產出的那一包是工作流的設計圖，稱為**藍圖包**，不是可以執行的完成品。「不可能這包就是工作流，應該說你現在作完的是工作流的設計圖」。

| 藍圖包內容 | 說明 | 依據 |
| --- | --- | --- |
| 詞彙表 | 沿用作者用詞 | 作者指定 |
| 合約與 schema | 每個階段的輸入輸出，各有白話合約與 schema | 作者指定 |
| 依賴清單 | MCP 等依賴，在安裝流程時由當下的宿主檢查 | 作者指定 |
| 流程的 `AGENTS.md` | 宿主 Agent 執行這條流程時的規則 | 作者指定 |
| `skills/` 資料夾與對應表 | 定義各步驟做法細節的 skill，可不只一個；對應表標出每個 skill 被哪些步驟調用 | 作者指定 |
| 缺口列表 | 還缺哪些確定性代碼與 MCP 調用，並標出既有 skill 內已經可用的代碼 | 作者指定 |
| 流程定義 | 步驟、順序、每步輸入輸出、檢核、審核方式、變數分類、工具清冊 | 紙上演練的彙整 |
| 任務設定檔樣板 | 「設定一次」那一組變數 | 作者示範的第七步 |

流程用到的 skill 一律整份放在 `skills/`，包含作者原有的 skill：「就把技能放在skills資料夾啊」。不拆出個別腳本，也不改成外部依賴。

各檔的檔名（`workflow.definition.json`、`glossary.json`、`contracts.json`、`dependencies.json`、`skill-map.json`、`gaps.json`、`task-config.example.json`）是 Agent 的提案。

範例：「虛擬IP粉專Reel製作與發布」藍圖包 0.2.1，13 個步驟、13 個 skill（流程專屬 11 個加作者原有的 2 個）、確定性代碼缺口 12 項、MCP 調用缺口 6 項。這份範例目前不在本 repo 內。

### 13.9 轉換器與底座首次安裝

作者的方向：「我們需要一個通用性的轉換器來將設計圖變成完成品」，並且「透過底座的首次安裝過程把它變成真實可用的工作流」。轉換器尚未設計。

現況（2026-11-20 讀本機 repo，底座 0.2.12）：

- 底座執行流程時，只載入 `flow.json` 指定的 wheel 內的 `adapter.py`，再逐步呼叫其中的 `handlers`（`flow_base/workspace.py`、`flow_base/engine.py`）。沒有任何程式會讀流程定義檔。
- Studio 的 Compiler 會把草稿編成 wheel（`compiler/generator.py`），只涵蓋確定性工具。

底座的流程更新功能（分支 `codex/workflow-zip-updates`，commit `ad8dbcb9`，2026-11-19 讀 `package_updates.py` 所得，未執行）收不下藍圖包：只收單層結構、檔名允許清單寫死、必須有唯一的 wheel、只更新不安裝、沒有宿主檢查依賴這一步。

轉換器要做的事（Agent 整理，不是定案的設計）：

1. 讀藍圖包，確認內容齊全且彼此一致。
2. 請當下的宿主依依賴清單逐項檢查。
3. 依缺口列表補齊確定性代碼並接上 MCP 調用，`skills/` 內已有的可用代碼直接取用。
4. 把 `skills/` 與 `AGENTS.md` 安裝到宿主讀得到的位置。
5. 產出底座能執行的完成品，並回報仍未補齊的項目。
