規格整理 v 1.2.2
開發規格草案 v1.0
專案名稱：RoutineKeel Workflow Compiler & Studio

核心目標：讓沒有程式開發經驗的人，透過業務描述、流程圖、操作影片或成功案例資料夾，由 LLM 自動完成工作流分析、設計、程式生成、測試及封裝，最後交由現有 RoutineKeel flow_base 穩定執行。

本規格以先前討論及已檢視的 RoutineKeel 儲存庫 為基礎，包含：
1. 技術規格文件：功能、架構、資料契約、執行邏輯、介面、狀態管理、跨平台、安全、測試與驗收。
2. 非技術規格文件：從一般使用者角度描述如何把業務工作轉換成可重複使用的工具。
3. Codex 分階段開發計畫：共 14 個階段（Stage 0～13），每階段都有可直接複製的 Instructions、預期檔案、測試、完成標準及回滾方式。
本次以新增功能為主，不重做現有 flow_base，也不直接變更現有字幕流程的業務規則。

1.2 欲解決的問題
目前新增一條工作流，仍需要具備一定工程能力的人整理業務邏輯、撰寫 Adapter 與 Handler、建立合約、測試，以及封裝。

本次開發要減少這些人工工程工作。

2. 目標、成功標準與範圍
2.1 產品目標
建立一個「業務流程自動編譯系統」，讓使用者只要提供任務目標及足夠的案例，便可以取得一份經過驗證的 RoutineKeel 工作流包。

使用者不需要編寫 Python、不需要手動設計每個節點，也不需要理解內部資料結構。

2.4 本次不做什麼
不建立全新的執行引擎、不取代 flow_base 佇列及成果管理、不自行實作通用雲端部署平台、不保證從單次成功案例推論出所有例外，不允許 LLM 在未經授權情況下任意執行系統指令或發布含外部副作用的工作流。

初版也不實作一般性的無限迴圈、任意動態圖重建或跨機分散式流程調度。

4. 基本設計假設與限制
本規格採以下假設，未經實測前不得視為已確認：
- A-01：新增模組設於 routinekeel/workflow_studio/，與現有 flow_base 保持分離。
- A-02：沿用專案目前使用的 Python 開發環境與測試習慣，不另指定新的技術框架。
- A-03：語言模型由可替換的供應介面提供，支援使用者自行設定可用模型及額度。
- A-04：第一個可交付版本以本機單使用者為主，不建立複雜帳號與多租戶體系。
- A-05：所有工作流生成與修改先在草稿區操作，只有通過驗證的版本才能正式發布。
- A-06：第一版優先生成靜態 DAG；簡單分枝可編譯為受控的複合 Handler，不要求修改現有 Runtime 的圖執行語意。
- A-07：影片分析只推導可觀察的行為，不把影片中未出現的判斷當成既定事實。
- A-08：未來可擴充多使用者與遠端服務，但本次不提前實作。

5.3 設計原則
1. Studio 與 flow_base 使用明確介面溝通。
2. Studio 不直接修改 flow_base 執行資料表。
3. 優先使用既有 WorkflowService，不得繞過既有安全及成果發布機制。
4. 所有 Compiler 模組可個別測試、替換。
5. 新 IR 有獨立版本，不取代既有 flow.json 的版本編號。
6. 新增任何 Runtime 擴充前，必須證明現有 Adapter 無法安全表達該功能。
7. 工具能力目錄只宣告可用工具，不代表自動授予執行權限。

流程控制規則
- 發現階段可以產生多個候選方案，不能自動把低證據可信度的推測變成已確認規則。
- 靜態驗證失敗不得進入動態執行。
- 動態測試只允許在隔離的測試工作區中進行。
- 自動修復須限制次數；預設最多兩輪，之後呈現失敗證據。
- 只有明確標記為可發布的版本才能進入正式流程目錄。
- 發布後修改必須產生新的版本，不得就地修改原有正式流程包。
- 不能從單次成功重播推導出整個工作流已涵蓋所有輸入與異常。

8. Workflow IR 技術契約
8.1 IR 與執行流程分離
新增 Workflow IR v1，作為 Compiler 的統一中介表示。

它不應等同於現有的 flow_base.contracts.Workflow。

流程為：

Workflow IR → 靜態驗證 → Lowering → 現有 Workflow/Step → Adapter/Handler → Package

其中 Lowering 需負責處理語意轉換與相容性限制。
8.2 基本資料模型
以下為概念範例：
{
  "ir_version": "1.0",
  "workflow_id": "course-subtitles",
  "revision": 3,
  "goal": {
    "description": "產生可供人工確認的字幕",
    "success_policy": "review_required"
  },
  "inputs": {
    "video": {
      "type": "file",
      "required": true
    }
  },
  "nodes": [
    {
      "id": "extract_audio",
      "kind": "deterministic",
      "tool": "media.extract_audio",

        "video": "input://video"

        "audio": {
          "type": "file",

8.4 變數參照與檔案位置
所有節點使用邏輯參照，不保存機器專屬的絕對路徑：
input://video
artifact://extract_audio/audio
output://subtitles
secret://provider_key


Runtime Adapter 負責將邏輯位置解析到本次執行工作區。

每個輸出必須同時具有：
- 穩定的邏輯產物 ID。
- 相對位置或受控儲存參照。
- 內容型別。
- SHA-256。
- 來源 Run、Step 及版本。
- 必要的完整性驗證資訊。
8.5 條件分支
初版只支援有限、確定性且可驗證的條件分支。

例如：
id: check_file
kind: composite_branch

condition:
  operator: file_size_gt
  input: input://file
  value: 104857600

branches:
  true: process_large_file
  false: process_small_file

output:
  schema: processed-file-v1


Lowering 必須將它編譯成現有 Runtime 可安全執行的複合 Handler；分支內部的結果都應符合共同輸出契約。

不得使用任意 eval、任意 Shell 指令或由文字直接執行未授權程式。

無法安全轉換的複雜分支須停止編譯。

9.4 新增、修改、刪除一致性
例如使用者刪除一個流程節點：
- 檢查是否有其他節點依賴它。
- 有依賴時要求先調整連線，或在同一筆編輯交易中完成更新。
- 產生新的 Revision。
- 讓受影響的測試與 Build 失效。
- 不刪除歷史 Revision 的節點。
- 既有正式發布版本保持不變。

12.1 基準效能測試
測試數值以下列固定測試集為準，硬體資訊及測試環境必須隨報告記錄：
- 100 個來源檔案的清單及基本中繼資料分析：不呼叫 LLM。
- 20 節點 IR 靜態檢查：目標 p95 小於 500 ms（不含檔案讀取及模型）。
- 100 次專案建立／更新／重開：不得產生資料損壞。
- 100 次不同輸入的流程執行：不得混合成果或識別碼。
- 20 個受控故障點：不得損壞上一個正式發布版本。
上述門檻應在指定硬體、SSD、本機及固定測試資料下驗證；不能推論為所有電腦的保證。

14. 驗收條件與 BDD 測試
AC-01：文字流程自動轉換
Feature: 將文字流程轉成可執行工作流

  Scenario: 有足夠條件的低風險流程
    Given 使用者提供工作目標、輸入與輸出
    And 流程包含三個可驗證的確定性步驟
    When 系統完成流程分析及生成
    Then 必須產生有效的 Workflow IR
    And 所有輸入輸出契約必須通過檢查
    And 必須產生符合 flow_base 契約的流程包
    And 必須通過正式測試後才能發布


AC-02：專案續編
Feature: 持續編輯工作流專案

  Scenario: 關閉後重新開啟
    Given 使用者已建立專案並儲存第三版草稿
    When 使用者關閉並重新開啟 Studio
    Then 必須還原第三版草稿
    And 還原來源參照與已保存證據
    And 已發布的舊版本不得被修改


AC-03：模型輸出失敗
Feature: 語言模型串流中斷

  Scenario: 收到不完整內容
    Given 語言模型正在輸出流程分析
    When 回應於中途斷線
    Then 畫面必須顯示中斷狀態
    And 不得將不完整內容標記為已驗證
    And 仍可重新開啟上一個有效草稿


AC-04：保護外部副作用
Feature: 外部副作用需要授權

  Scenario: 未授權的寄送節點
    Given 生成流程包含對外寄送動作
    And 尚未取得需要的授權
    When 使用者嘗試發布工作流
    Then 必須拒絕發布
    And 顯示待授權的操作與原因
    And 不得執行寄送


AC-05：執行期不必要的 LLM 呼叫
Feature: 確定性流程執行

  Scenario: 流程不包含 LLM 節點
    Given 已發布的流程只包含確定性 Handler
    When 使用者透過 flow_base 執行流程
    Then 工作流必須正常完成
    And 流程直接呼叫的 LLM API 次數必須為零


AC-06：資料夾來源驗證
給予一組已知輸入、完整中間產物及正式成果，系統應能產生候選資料流、指出每項依賴的證據、執行 Golden Case 重播，並對無法證明的步驟保留待確認狀態。
AC-07：跨平台
同一份 IR 必須可以產生平台需求報告。若 Windows 可執行而 macOS 缺少必要工具，系統須明確標註 macOS 不支援，不能宣稱已通過跨平台驗證。
AC-08：影片推導
對包含已知 5 個操作步驟的固定測試影片，應產生具有時間位置及來源證據的候選操作表；無法辨識的操作不得被標成已確認，也不得僅憑影片就自行授權正式執行。

第二部分：非技術規格文件（白話版）
本部分專供沒有程式開發經驗的使用者閱讀。
1. 這個工具要做什麼？
RoutineKeel 將新增一個「工作流程製作工作台」。

原本，你可能知道如何完成某件工作，卻不知道如何把它做成其他人可以一鍵使用的工具。

新的工作台會協助你把現有工作方法整理成可重複使用的流程。

例如，你平常要處理課程影片：
1. 找到影片。
2. 產生字幕。
3. 檢查字幕是否正確。
4. 製作交付檔案。
5. 請老師確認。
你不必逐步教電腦如何寫程式，只需要告訴它要完成什麼工作，並提供能讓它理解工作方法的資料。
2. 可以提供哪些資料？

文字說明

用自己的話描述工作，例如「先整理檔案，再轉換格式，最後產生報告」。



流程圖

上傳手繪圖或提供現成流程圖，讓工作台理解工作順序與不同情況的處理方式。



一個已成功完成工作的資料夾

裡面可以有原始資料、過程中產生的檔案、最後成果，以及操作紀錄。



操作影片

提供實際完成工作的錄影，系統會嘗試辨識操作順序與使用的工具。此功能安排在後續擴充階段。



你可以同時提供多種資料。提供的資訊越完整，通常越有助於確認實際工作方法。
3. 一般使用者怎麼操作？
1. 建立一個工作專案
   
   幫它取個名字，例如「課程字幕製作」。寫下你希望完成的任務，以及最後想得到哪些檔案。
2. 提供一個已完成的例子
   
   選擇文字、流程圖、資料夾或影片。上傳前後可以先預覽內容，確認選對資料。
3. 讓系統整理工作方法
   
   畫面會逐步顯示理解到的工作步驟，並標記哪些內容已經確認、哪些仍不確定。
4. 查看與調整流程
   
   不需要編寫程式。你可以改名稱、調整步驟順序、選擇不同的處理方法，或回答幾個重要問題。
5. 進行試做
   
   系統使用你提供的測試資料實際試做，並將結果與你認為正確的成果比較。
6. 確認並發布
   
   當成果符合要求，就可以保存成一個日後反覆使用的工具。

4. 畫面會長怎樣？（SVG 示意）
左邊提供工作範例，中間看工作順序，右邊查看問題與試做結果。
畫面預設使用明亮的白色與淡灰色背景，藍色代表主要操作，綠色代表已完成，橘黃色表示需要確認，紅色表示無法繼續。

6. 使用上的限制
工作台不保證只看一份成功成果，就能理解所有可能發生的情況。對不確定的內容，它會保留問題，而不是自行編造規則。

操作影片也可能因為畫面不清楚、錄影不完整或部分動作沒有顯示，而無法還原所有工作步驟。

系統完成試做，不代表所有業務情況都已經驗證成功。正式使用前，仍應檢查結果是否符合自己的要求。

涉及刪除重要資料、對外寄送、修改其他系統內容等操作時，可能需要另外確認。
7. 專案管理
使用者可以：
- 建立與重新命名專案。
- 隨時儲存草稿。
- 關閉後繼續上次進度。
- 替換或移除已提供的資料。
- 修改工作步驟並保存新版本。
- 查看舊版本和試做結果。
- 封存不再使用的專案。
- 保留已正式使用版本的歷史紀錄。
使用者不用從頭重來。 即使後續補充新的範例，也可以從現有專案繼續修改。

第三部分：Codex 分階段開發計畫
1. 開發策略
本次拆分為 14 個 Stage（Stage 0～13）。

每個 Stage 都需完成程式修改、測試、文件更新及 Git Commit，驗收成功後才能進入下一階段。
開發階段總覽
1. Stage 0：建立專案骨架與規範 — 建立基礎結構、開發指引、測試及持久化策略。
2. Stage 1：建立專案管理與持久化 — 支援 CRUD、版本及續編。
3. Stage 2：實作來源匯入與預覽 — 處理文字、Mermaid、檔案及資料夾。
4. Stage 3：建立 Workflow IR 與合約檢查 — 定義可編譯的統一流程格式。
5. Stage 4：建立工具能力目錄 — 找到可重用的 Handler。
6. Stage 5：實作文字與 Mermaid 流程發現 — LLM 自動解析業務描述。
7. Stage 6：實作成功資料夾逆向分析 — 從成果與證據推導候選流程。
8. Stage 7：實作 Compiler 與流程包生成 — 產出符合 flow_base 的工作流。
9. Stage 8：建立獨立驗證與自動修正 — 重播、比對、測試與有限次修復。
10. Stage 9：支援條件分支與執行期 LLM 隔離 — 增加必要的動態能力。
11. Stage 10：加入操作影片分析 — 擴充多模態流程證據。
12. Stage 11：完成 Studio 工作台與人工發布治理 — 實現非技術人員操作閉環。
13. Stage 12：補齊整合、回歸及邊界測試 — 跨平台與可靠性驗證。

# RoutineKeel Workflow Studio — Codex Working Agreements

## Project goal
Develop a Workflow Compiler and Studio that converts business-process
evidence into tested, versioned, executable RoutineKeel workflow packages.

## Scope
- Main implementation: routinekeel/workflow_studio/
- Tests: tests/studio/

- Preserve existing CLI, MCP, workflow manifests, and releases.

- Make small, reversible changes.
- Separate workflow design from runtime execution.
- Every new object supports create, read, update and delete/archive.
- Projects must persist and reopen correctly.
- Every accepted upload must have a usable preview.
- Preserve aspect ratio during display scaling.
- All visible LLM output must stream.
- Treat external inputs and model outputs as untrusted.

- Preserve existing public contracts unless migration is approved.

- Run relevant existing flow_base regression tests.
- Report skipped tests separately from passed tests.
