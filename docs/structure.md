# 目錄與協作方式

RoutineKeel 是對外專案與工作區名稱，flow_base 是共用執行底座。這次更名不改 Python namespace、CLI 名稱、既有 flow_id／run_id 或歷史工作指紋。

## 使用區與開發區

| 位置 | 責任 | 維護原則 |
| --- | --- | --- |
| 根 README.md | 給非技術使用者的介紹與上手入口 | 不把底層開發細節塞進操作步驟 |
| flow_base/ | 已封裝的共用 runtime 與一鍵入口 | 由 source/base 與共用打包工具產生 |
| 課程影片產生字幕/ | 已封裝字幕流程 | 領域設定、字幕、人審與資源宣告都留在此包 |
| 檔案複製範例/ | 第二個獨立流程 | 驗證多流程共用一份底座 |
| source/base/ | 底座完整原始碼 | 環境、資源、狀態、紀錄、用量、通用派送 |
| source/ai_flow01/ | 字幕流程完整原始碼 | VAD、ASR、時間軸、品質與人類確認介面 |
| source/ai_flow02/ | 複製流程完整原始碼 | 最小領域範例，內部名稱不影響友善顯示名稱 |
| source/tests/ | 跨包整合測試 | 驗證契約、解耦、搬移、快取與啟動器 |
| source/tools/ | 發行與指引生成 | 不把大型環境與模型帶進套件 |
| assets/ | 使用者提供的品牌素材 | 原檔保存，以相對路徑引用 |
| docs/ | 專案層級維護說明 | 套件細節仍由各自 README 維護 |
| downloads/ | 可分享的 RoutineKeel 啟動 ZIP、SHA-256 與版本清單 | 從乾淨發行快照生成 |

根層執行包中的 source.zip 是原版分包保留的原始碼快照，方便只拿單一套件的人追溯；日常開發修改 source/，不要同時維護兩份解壓副本。

## 工作區會自行長出的資料

`.venv`、`share_states`、`share_logs` 在 RoutineKeel 根層建立；各流程的成果位於自身 `outputs/<工作>/`。這些是使用者的執行資料，不進版本控制，也不進學員分發包。未使用前看不到這些資料夾是正常情況。

每個流程可以單獨改顯示名稱或資料夾名稱；共用底座的資料夾仍保留 flow_base，方便既有薄入口找到它。flow_id 自動註冊，run_id 每次執行建立，不以 ai_flow01 這類內部開發名稱要求學員記憶。

## 解耦邊界

底座偵測並提供共用環境資訊，流程決定模型及 CPU／CUDA 策略，並驗證實際可用的後端。底座記錄進度與用量，流程定義節點與領域結果。底座提供通用 action 派送，流程決定匯入、重建、恢復或真人核准的具體規則。

因此可以只更新底座、只更新字幕流程，或新增第三個流程，不必把三者合併成單一巨型程式。
